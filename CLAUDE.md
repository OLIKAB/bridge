# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Bridge, a macOS menu bar app for developers: a Swift package (`Package.swift`, macOS 14+, no external dependencies) with the app (`Sources/Bridge`) and a `Shared` library of panel controls and system integration (`Sources/Shared`), which is also a library product so other menu bar apps can build on it. Keep `Shared` free of anything Bridge-specific.

The panel has two tabs: *Repos* (git repositories with quick commit/pull/push, plus a GitHub Desktop–style main window with changes, history, diffs; runs a repo's dev server in the background and opens a coding agent in the terminal) and *Servers* (processes listening on local ports, dev servers and Docker, with CPU/memory usage, favorites that can be started, restart/stop; code in `Sources/Bridge/Servers`).

There are no tests and no linter configured.

## Commands

```sh
swift build                      # debug build (quick compile check)
swift run Bridge                 # run unbundled (no Info.plist/icon; fine for quick checks)

./build.sh                       # universal release build into build/Bridge.app
./build.sh --install             # also copy to /Applications, kill the running copy and relaunch
./build.sh --dist                # also create dist/ zip and dmg
NOTARY_PROFILE=<profile> ./build.sh --dist   # Developer ID + hardened runtime, notarized and stapled
                                 # (profile from `xcrun notarytool store-credentials`)
./build.sh --release             # ship an update: --dist, then a GitHub release bridge-v<VERSION> with the zip and dmg
                                 # (raise VERSION in build.sh first; UPDATE_REPO=owner/name for another repo)
```

The website, bridge.olikab.com, is one static page in `website/` on Vercel (`cd website && vercel --prod`; the subdomain is a CNAME to `cname.vercel-dns.com` at Webhuset, as for the owner's other sites): one screen with no scrolling, an aurora in the knot's colours, the line, and Download. Under the button is a loop recorded in the real app with demo repositories (`assets/demo.*`), framed, as large as the room left under the line allows (a size container), with the same room above the line as below the loop; tall, narrow screens get the panel alone (`assets/demo-mobile.*`) through the sources' media query. The page is set in SF Pro (the system font, as in the panel; an italic Instrument Serif headline was dropped as the font every AI landing page uses), with Geist from `website/fonts` standing in off the Mac, the aurora draws at most 30 frames a second, and `website/vercel.json` sets caching. A click on it or "Watch the demo" opens the whole 36-second recording (`assets/demo-full.mp4`), the only video with sound: a quiet synthesized ambient pad, no sound effects or voice, laid under it by `./scripts/add-demo-audio.sh` (run it again after re-recording; the loops stay silent, as autoplay has to be muted). Tried and dropped: the page as a Mac screen with the panel hanging from a menu bar knot, a tilted plane, a glass plate, the panel alone with feathered edges or lit by a blurred copy of itself, and an HTML-drawn panel. Its Download link goes through `/download` (a redirect in `website/vercel.json`) to the worker in `telemetry/`, which counts it and sends the newest release's .dmg; the same worker takes the app's daily anonymous ping (`UsagePing`). `./scripts/usage-stats.sh` prints the numbers.

`build.sh` generates the `Info.plist` (including `LSUIElement`, bundle id `com.olikab.bridge`, version, `UpdateRepository`) — there is no checked-in plist. It signs with the first Apple Development or Developer ID certificate in the keychain (ad hoc without one). Releases must keep being signed by the same team: `AppUpdate` only installs an update signed by the same team as the running copy.

The app icon is rendered in Blender (`Blender -b -P scripts/make-bridge-icon.py`, about two minutes on the GPU): the knot, three Borromean rings woven in 3D (A over B, B over C, C over A) in white ceramic lit by a mint, a violet and a coral strip light. It also writes `Resources/Brand` (the 1024 px icon, a transparent 2048 px knot for the website, a 2400×1260 banner for link previews) and uses a render with thicker rings for 16 and 32 px, where the weave is too fine to read. The flat marks there (`bridge-mark.svg` in the three colours, `-black`, `-white`) and the menu bar glyph (`KnotMark.swift`, a template image with gaps cut where a ring passes under) draw the same rings on the same 100-unit grid; change all of them together. The installer background (`scripts/make-bridge-dmg-background.swift`) is lit by the same three colours.

## Architecture

The app follows the shape of a menu bar app built on `Shared`:

- `BridgeApp.swift`: `@main` SwiftUI `App` with a single `MenuBarExtra` (`.menuBarExtraStyle(.window)`), and a `HotKey.shared` extension defining the app's global shortcut (⌥⌘ + letter, unique four-char signature). Bridge has one per tab (`HotKey.repos` ⌥⌘G, `HotKey.servers` ⌥⌘P) in `Panel.swift`, where `BridgePanel` switches between the tabs' panels. A tab once shown stays built (`TabStack` puts the hidden one outside the window, offered the same size, so a switch reuses its layout and layers); rebuilding a tab on every switch, or flipping `.disabled`/`.accessibilityHidden`/`.opacity` on a whole tab, held the main thread 40–100 ms. So a tab's `onAppear` doesn't run on a switch, its shortcuts sit in `TabShortcuts`, and the tab switch on macOS 27 is one `NSSegmentedControl` (role `.tabs`, which has the Liquid Glass lens) drawn by `BridgePanel` over the room each header keeps for it (`PanelTabs`).
- A `@MainActor ObservableObject` store (`RepoStore`, `PortModel`) owning state, polling/scanning, and settings persisted in `UserDefaults` via `didSet` on `@Published` properties.
- `MenuPanel.swift`: the panel UI. Slow work (file system scans, libproc, git) runs off the main thread.

`Sources/Shared` holds what isn't particular to Bridge:
- `MenuBarPanel.swift` — workarounds for `MenuBarExtra` sizing: `.fitsMenuBarPanel()` (shrinks the panel window back to its content) and `MenuPanelList` (scrolls past a max height without collapsing). Use these instead of a plain `ScrollView` in panels.
- `SystemIntegration.swift` — `HotKey` (Carbon, no Accessibility permission needed; toggles the panel via `MenuBarPanel.toggle()`), `LoginItem`, `Notifier`, and `RenamedApp.migrateDefaults` (copies settings once from an app's earlier bundle ids, for apps built on `Shared` that were renamed).
- `DevWorkspace.swift` — detects a project's dev start command (package.json script + lockfile-derived package manager, with an install-if-stale check; Django/Rails/Laravel/compose/etc. fallbacks) and opens Claude Code in Terminal via a generated `.command` file (avoids AppleScript permission prompts). Used by Bridge.
- `Integrations/` — adapters for the tools Bridge drives, so it isn't tied to one developer's setup: `CodingAgent` (Claude Code, Codex, Cursor CLI, Gemini CLI, Copilot CLI, OpenCode; `CodingAgents.current` is the first installed, chosen by `choose(path:)` when the panel opens; each agent lists its `AgentCapability`s, and one whose flags aren't documented doesn't get the capability) and `TerminalApp` (`Terminals.current`, the first installed of Rex, iTerm, Ghostty, Warp, WezTerm, kitty, Terminal; each runs Bridge's script file its own documented way without Automation permission: opening the file, its CLI, or for Warp a Tab Config in `~/.warp/tab_configs` opened by `warp://tab_config/<stem>`). Bridge's `GitHost` (`GitHost.swift`: `GitHubHost` through `gh`, `GitLabHost` through `glab`, run via `HostCLI`) is the same for publishing, cloning and pull/merge requests; a repository's host comes from its web page (`Repository.host`), the accounts are `HostAccount.shared(for:)`, and Publish and Clone offer a host picker only when both CLIs are installed (`GitHosts.available`). `glab repo create` neither adds a remote nor pushes, so `GitLabHost.publish` does both with git. Agent and GitLab logos are Simple Icons in `Resources/Logos`, loaded with `Logo.bundled(_:fallback:)`. Go through these rather than naming `claude`, Rex or Terminal in new code. In Bridge, `AgentStatus.shared` (looked up when the panel opens, publishes only on change) gives `AgentInfo`, handed to rows in `RepoRowOptions`: show anything agent-related only behind `info.can(.capability)` (installed and capable), and name it with `info.name` and `terminalName` rather than "Claude"/"Terminal". Without an agent installed, no agent buttons show at all. Claude-only features (background sessions, skills, updates, usage) still run `Claude.executable`. The user picks agent and terminal in Settings (`AgentPicker`, `TerminalPicker`; "Automatic" is the first installed, "None" hides everything agent-related; a picked agent that isn't installed stays picked so the checklist offers to install it) and on the setup page (`SetupPage`, `PanelPage.setup`), shown once to a new user with no repositories and from Settings › Set up Bridge…. `AppUpdate` checks GitHub Releases on `UpdateRepository` (Info.plist, from `UPDATE_REPO` in `build.sh`; `bridge-v<version>` tags) every six hours and from Settings; the panel's top line then offers Update, which downloads `Bridge-<version>.zip`, installs it only if it's Bridge at that version with a valid signature from the same team as the running copy, and swaps it in with a script that waits for Bridge to quit, then reopens it. Failed checks are silent; the repository must be public for the unauthenticated API.
- `Editor.swift` — "open in" editor list (editors, then the current terminal), `IconButton`, `Logo.claude`.

Notable platform choices (preserve them unless there's a reason not to):
- Bridge shells out to the `git` and `claude` CLIs rather than using libraries, so the user's config, keys, hooks and Claude login apply. Its main window is an `NSWindow` managed by hand (a SwiftUI `Window` scene would open at launch); the app shows in the Dock only while it's open.
- Bridge's groups (`Groups.swift`, `RepoGroups.shared`) are shared by both tabs: a repository is put in a group by hand, a server inherits the group of the repository its project folder is in unless it has its own (stored by `favoriteKey`). A group exists only while something is in it. Rows are dragged between groups (`GroupDragItem`, a private UTType so a drop on a text field doesn't paste text); every row and header of a section is a drop target, and the ungrouped "Other" section shows only when something is in it (with everything grouped, a row leaves its group from its right-click menu). Groups show as foldable sections in the panel (folded state per tab) and as sidebar sections in the main window; with no groups the lists look as before.
- Bridge's Servers tab reads processes/ports via libproc/sysctl (`NativeProcess.swift`) instead of spawning `lsof`/`ps`; only the current user's processes are visible.
- Bridge starts background Claude sessions with `claude --bg` (no Terminal window) and follows them via `claude agents --json` and each session's `~/.claude/jobs/<id>/state.json` (`BackgroundClaude.swift`). Answering one stops it and resumes it with `--bg --resume`, since a running background session can't be typed into.
- The top line of Bridge's panel (`ClaudeUpdate.swift`) compares `claude --version` with the newest version it can actually update to (the Homebrew cask's, from formulae.brew.sh, for a cask install, as the cask is often hours behind npm; npm's otherwise) and updates with `brew upgrade --cask` or `claude update`. An update the updater turns out not to have is dropped quietly, not reported in red. The usage left there comes from `~/.claude/rate-limits.json`, which the user's status line script (`~/.claude/statusline.sh`) writes from the `rate_limits` Claude Code passes it; Bridge doesn't read Claude Code's login from the keychain.
- Everything Bridge spawns (dev servers, git, Claude Code's daemon when Bridge starts it) runs with Bridge's privacy access to ~/Documents and the like, which is tied to the code signature. So `build.sh` signs Bridge with a real certificate too; with an ad-hoc signature those processes fail with EPERM after every reinstall.
- The framework logos in `Resources/Logos` are Simple Icons SVGs (CC0), copied into the bundle by `build.sh`.

## Menu bar panel sizing

`MenuBarExtra` sizing has bitten every app. Known failure modes and what causes them:

- **Panel stays too large / dead space at the bottom** after content shrinks (e.g. toggling "show system" off): `MenuBarExtra` only ever grows its window. The panel's root view needs `.fitsMenuBarPanel()`.
- **Panel is empty or collapses to nothing**: a plain `ScrollView` has no intrinsic height inside `MenuBarExtra`. Use `MenuPanelList(maxHeight:)`.
- **Panel never shrinks below some size**: a fixed `.frame(height:)` or `minHeight` anywhere in the content becomes the window's minimum. Use `maxHeight` only.
- **Panel jumps on open / content looks slightly smaller than the window**: height measured into `@State` (GeometryReader/PreferenceKey) is zero for the first frame. Don't measure; let `MenuPanelList` lay it out.
- **Panel ends up the wrong size and can't scroll after rows are added at once** (opening a folded group in Bridge): `MenuPanelList` used to switch between bare rows and a `ScrollView` (`ViewThatFits`) at the max height, which rebuilt the rows mid-resize. It's now always one `ScrollView`, as tall as its ideal (content) height up to the max. Don't animate changes to the panel's height either.

When changing panel layout, check it in the installed app (`./build.sh --install`): open the panel, toggle whatever adds/removes rows both ways, close and reopen, and confirm there is no empty space and no clipped content.

## Dev start command (`DevWorkspace.startCommand`)

The command runs in a fresh login shell in projects Claude hasn't seen, so it must survive a missing or half-finished install. Real cases it has to handle:

- `sh: nuxt: command not found` / `concurrently: command not found`: `node_modules` exists but the install was interrupted or predates `package.json`/lockfile changes. A bare `node_modules` folder is not proof of an install; `dependenciesCurrent` compares the package manager's completion marker against `package.json` and the lockfile.
- Fresh clone with no `node_modules`: install first, with a status line (`say`) so a long silent install doesn't look stuck.
- App not at the repo root (e.g. `nuxt/frontend/package.json`): when the root has nothing, the shallowest subfolder (up to 3 levels, skipping node_modules/build folders, preferring names like `frontend`/`web`/`app`) is used and the command starts with `cd <folder> &&`. Repos with several apps: the user picks one in Bridge's start command editor (`Repository.startFolder`, stored per repo); a pick whose folder no longer has a command falls back to the automatic choice.
- Package manager comes from the lockfile (pnpm/yarn/bun/npm), never assumed to be npm; yarn Berry uses a different marker than yarn 1.

When touching this code, test the generated command by hand in such a project (delete `node_modules`, or `touch package.json` after an install) and confirm it installs, then starts.

## Install after every change

After every finished code change, run `./build.sh --install` without being asked, so the installed app always matches the code. Skip only when told not to or nothing app-facing changed, and say in one line that it was skipped.

## Look and feel

Use the system's own controls and colors rather than drawing them, so the apps look like macOS's own menu bar panels:

- Every small control has the same hover and press feedback (`Shared/PanelControls.swift`): icon buttons are `IconButton` or `.buttonStyle(.panel)`, on/off icons in a panel are `PanelToggleBar([PanelToggleItem(…)])`, the system's segmented control with any number of segments on (`selectAny`), so a switch never looks like a button that opens or runs something and looks like the tab switch (a drawn tray of drawn switches was tried first, and its on state never looked right; each segment's tooltip goes through `PartTooltips`, as `panelTooltip` can't sit on a segment); `Toggle(isOn:) { … }.toggleStyle(.panel)` is left only for the main window's glass toolbar icons, icon menus `PanelMenu(_:help:)` (a borderless menu shows nothing under the pointer; it has a small chevron after the icon, as anything that opens a menu should, like the branch chip), chips `.buttonStyle(.panelChip)`. Text buttons are Liquid Glass: the panel, the main window and every popover's content get `.glassButtons()` (`.glass` for buttons without a style of their own; a popover doesn't inherit it, so popovers are `panelPopover`), and a line's or form's main action is `.prominentButton()` (`.glassProminent`; a glass button with the default action's shortcut isn't tinted by itself). Never `.bordered` / `.borderedProminent`: they're flat beside the glass tab switch and switches. Picking one of a few views or sources (Memory/CPU, Changes/History, GitHub/GitLab, All/This project) is `PanelSegments`, AppKit's segmented control in the tabs role, which has the glass lens and grey raised selection like the Repos/Servers switch; SwiftUI's segmented picker can't ask for that role and draws a flat blue selection. On/off switches stay `PanelToggleBar`, blue while on: the system gives a segmented control with several segments on no glass, and glass toggle buttons looked like the buttons beside them that run something.
- Fills: the semantic `.quaternary` / `.quinary` styles, not `Color.primary.opacity(x)`. Rounded backgrounds inside a panel use `panelBackground` / `panelHighlight` (`Shared/MenuBarPanel.swift`): on macOS 26 their corners are concentric with the window's, as in the system's own panels. No hard-coded corner radii. A row's hover highlight is inset 6 pt from the panel's edge like a sidebar's.
- Tooltips only on controls that are just an icon (icon buttons, icon switches, icon menus, swatches): `panelTooltip(_:)` (`Shared/PanelTooltip.swift`), never `.help`. macOS's tooltip material, in a window of its own so the menu bar panel's edge doesn't cut it off, first line the name and further lines in grey, just above the control after 0.45 s (at once when moving on from another tooltip), up to 380 pt wide so it stays a line or two. No tooltips on rows, fields, badges, counts, chips, links or text buttons: they were everywhere, got in the way of what was being reached for, and felt home-made; those say what they are. `IconButton` and `PanelMenu` already have one.
- Small confirmations: counts in badges are `RollingCount` (roll like an odometer, count down to 0 and fade after a commit or push); copying goes through `Pasteboard.copy` and confirms with `copiedConfirmation(_:)` (`Shared/CopiedConfirmation.swift`) on the thing it was copied from (the row, for a context menu), keyed per item so only that row shows it; a label that changes with ⌥ crossfades with both texts laid out, so its button keeps its width. The panel opened again within a minute is as it was (open row in view); later it opens fresh at the top (`PanelState.isReturningLater`). The menu bar knot is a status light (`KnotMark.Lit`): each ring is solid while what it stands for is in use and faint otherwise, so the knot stays whole: code (top) while a repository has local work, server (bottom left) while a dev server runs in a repository (`server.isActive`), agent (bottom right) while a background Claude session works or waits, with a dot while one needs an answer. Beside it, the number of repositories with local work, only when there is some: a count for code, where server and agent are on or off. The total number of repositories was shown too, but it hardly changes and only took room. Stronger weight instead of faintness was tried in a sketch and can't be told apart at 18 pt.
- A text field and everything in a line with it are the system's controls at the regular size, where they're all 24 pt tall with the same 6 pt corners: buttons there use `.fieldRowButton()` (`prominent: true` for the line's main action, with an optional `tint`; it also brings a symbol-only button up to a text button's height), switches a `PanelToggleBar` at `.regular`. Not `.large`: since macOS 26 large buttons and segmented controls are capsules 26–28 pt tall while the field stays a 24 pt rounded rectangle, so a line never matched. Measure a change in a small window built from `Sources/Shared` (heights with a `GeometryReader`, corners and text inset from a zoomed screenshot). Drawn fields and buttons were used while the app was linked as for macOS 14 and got the old system controls (see `currentSDK`); with the real SDK the system's own look at home and match each other.
- Every text field, in panels, popovers and the main window, uses `panelField()`: the system's `.roundedBorder` field at the regular size. Focus shows as its hairline turning the accent color (1 pt, 80 %), drawn over it by `panelField`, instead of the system's focus ring, a thick glow outside the field that looked heavy in a small panel and was cut off by the rows around it. Don't fade in a line holding a field or a prominent button (`revealsGently`): the system's materials draw black until the layer is opaque. Text laid over one (a placeholder that changes often, "Claude is writing…", "Write with Claude ⇥" at its end while it's empty) is inset `PanelMetrics.fieldTextInset`. In a `Form`, wrap it in `LabeledContent("Name") { TextField(…).labelsHidden() }`, as a plain field isn't labelled by the form.
- Bigger forms that don't belong to one row (New project, Clone in Bridge's Repos tab) open as a page of the panel (`PanelPage`, `PanelPageHeader`), in place of the list, as Control Center opens Wi-Fi in its own panel: a "‹ Repos" back button where the tabs were (Esc too), the title in the middle, the form's first field focused, its primary button `.prominentButton()`, and a line saying what will happen. Pages come in with `slidesIn(from: .trailing)`, the list comes back with `.leading`; when done, the list shows what was started at its top (Setting up / Cloning). Small forms tied to one row (skills, start command, rename, publish) stay popovers anchored to that row. The main window keeps popovers for both.
- Claude writing a commit message is part of the field, not a button beside it (`claudeWrites(isEmpty:isWriting:action:)`): an empty field ends in a grey "Write with Claude ⇥" (Tab or a click), the field says "Claude is writing…" in shimmering grey (`ShimmerText`) meanwhile, and the result is written in with `PanelMotion.typeOut` on the shimmer's beat (it waits `ShimmerText.untilPassEnds()`, under 1.2 s, so the light finishes its pass and the text follows it rather than cutting it off) (a few words at a time, done within half a second, never over text the user typed meanwhile). No sparkles icon and no colored rings or glows: tried, and they looked like AI decoration out of place among the panel's plain grey controls.
- Motion (`Shared/PanelMotion.swift`) only shows what a click did, and never animates the panel's height: `revealsGently()` on content a click opens (details, a group's rows, notices: fades in and settles 4 pt; closing is immediate), `disclosureRotation(_:)` on chevrons. Hover feedback is never animated, as in macOS's menus: a highlight that glided from row to row or faded in was tried and made the panels feel like they lagged behind the pointer. `fadesIn(_:)` swaps things in place at once. Highlights keep `PanelMotion.highlightGap` above and below, so two lit rows side by side (one hovered, one open) don't merge.
- Buttons that show on hover are always laid out and only faded (`fadesIn`), never added with `if hovering`, so the name beside them isn't cut shorter under the pointer. Rows that open on a click end their hover buttons with a disclosure chevron, so it's findable that they open.
- A row whose resting badges give way to buttons on hover lays out both in a `ZStack` and fades one out (`RepoRow`, `ProcessRow`), so the name doesn't shift. While one of its popovers is open the row stays as under the pointer (`RepoRow.isActive`), and popovers are anchored to the whole top line, so they don't move when the pointer passes over the row.
- Something hidden with `.opacity(0)` still takes clicks: add `.allowsHitTesting(false)`.
- Servers rows follow `RepoRow`'s pattern (one line, buttons on hover, details behind a click, one open at a time in `ExpandedServer`).
- The main window has to work at any size, including below its own minimum: window managers, tiling and System Events resize it without asking it. Content wider than the window is centered and cut off on both sides, so: the panes (sidebar, list, diff, notes) are `HSplitView` panes whose narrowest and widest sizes come from `MainLayout.Widths` for the window's current width (minimums shrink in proportion below the normal sum, notes that don't fit stay closed, and the panes beside the diff are capped so the split view, which only shrinks its last pane, can't push the rest out). The window's width is measured with a `GeometryReader` around the content, never on the content. The sidebar hides by itself when narrow (⌃⌘S brings it back); the window only widens itself for what the user switches on (`requireContentWidth(grow:)`), never because the layout changed on its own. The split views are rebuilt (`.id`) when a pane comes or goes, as they kept stale widths otherwise. Top bar buttons, the Changes/History switch and `PathLabel` step down to shorter forms with `ViewThatFits`. Notes are a split view pane, not an `.inspector`. The top bar shares the title bar's row with the traffic lights: an empty `.unifiedCompact` toolbar makes the title bar 40 pt, exactly `MainLayout.barHeight`, so the panes below start where the title bar's safe area ends (a bar shorter than the title bar left panes overlapping it, and each split view pane, hosted on its own, took that overlap as an inset or, ignoring it, stretched up under the bar). Test a layout change by resizing with System Events (`set size of window`) across 450–1700 pt wide and 450–1000 tall, shrinking as well as growing, with notes and the sidebar on and off, and with a commit open in History.
- The main window has no menu bar of its own, so its shortcuts sit on hidden buttons: ⌘B branches, ⌘R fetch, ⌘P push, ⌘⇧P pull, ⌘1/⌘2 Changes/History, ⌘F filter, space stages, Delete discards.
- What users try first, and what it does: in Repos, ↑/↓ in the prompt field selects a row, Return runs the prompt in it (or opens it), Esc steps back one thing at a time and finally closes the panel, a double-click opens the main window, folders dropped from Finder are added, the branch chip is a branch menu, ⌘R/⌘N/⌘O fetch/new project/add. In Servers, a double-click opens the app in the browser, ⌥ turns stop into force stop, ⌘R refreshes, servers stopped from Bridge stay for the session to start again (`recentlyStopped`). In the main window, ⌘W closes, ⌘C copies paths or the SHA, History has a search field and a commit's right-click menu has Undo commit, Revert, Create branch and Switch to.
- Repository rows are dragged with `repoDragRow` (`RepoDrag.swift`): into another group (dropped on a row or header there), and to another place among the repositories the sorting puts beside them, which is only within a color (and favorites or not) while sorted by color (`RepoStore.manualOrder`, `reorderBlocker`). While it's held over a row, a thin accent line shows where it lands; where it can't go, the pointer shows macOS's "not allowed" sign and the row says why in a small capsule. `.onDrag` rather than `.draggable`, as the rows need to know what's dragged before it's dropped.
- A double-click goes beside the single click (`simultaneousGesture`), not before it, so the single click isn't delayed. Panels that take keys while open use a local `keyDown` monitor that only acts while it has something to act on (a search, a selection), so text fields keep Return and Esc.
- Don't name a generic parameter of a shared view after a SwiftUI type (`Menu`, `Label`): the compiler errors it gives are hard to read.
- Lines between parts of a panel (header, notices, list) are `PanelDivider`, inset to the content's edge like the separators in Control Center's panels. Between rows and before each group: `PanelDivider(subtle: true)`. Group headers look like sidebar section headings.
- Rows are built to be scanned (`RepoRow`): one line with only what's particular to the repository (changes, ↑/↓, a running app's port, a Claude session's state), the buttons in its place under the pointer, and the rest (status in words, skills, sessions, commit field) in the row opened by a click, one at a time (`ExpandedRepo`). Repositories with nothing going on are dimmed. Color only where something needs you.
- A repository's color is a short stripe before its logo, inside the row (`RepoColorStripe`); a click on it opens a palette of swatches. Only rows with a color make room for it, so those names sit a little further in. Tried and dropped: a margin every row kept for the stripe (indented every uncolored row), keeping it only while some row had a color (the whole list shifted when the first color was set), the stripe in the row's 8 pt margin (cramped against the logo) and in the gutter outside the highlight (against the panel's edge, and clicks didn't reach it).
- The favorite star sits at the start of a row, before the logo (`LeadingStar`, both tabs). Favorites always show it; on other rows it slides in, pushing the name aside, only while the pointer is at the row's leading edge (`tracksLeadingEdge`), the one hover change that moves something, as the user asked for. Row top lines are `PanelRowMetrics.lineHeight` tall in both tabs, so Repos and Servers rows match. On rows without a color, an empty color stripe slides in beside the star the same way, to click for the palette (`RepoColorPalette`).
- `Package.swift` links the apps with the real SDK version (`currentSDK`). Without it SwiftPM records sdk 14.0 and macOS runs the apps in compatibility mode: no Liquid Glass, small square-ish panel corners, old text fields. Check with `otool -l <binary> | grep -A4 LC_BUILD_VERSION`.

Hover: a row with `.onHover` needs `.contentShape(Rectangle())`, or only its visible parts take the hover (a clear highlight doesn't). And whatever appears on hover must not change the row's height (buttons `.controlSize(.small)` in a line as tall as the resting state), or the row moves out from under the pointer and flickers.

Smoothness: a row must not observe a store that forwards every repository's changes (`RepoStore` does, for sorting and the menu bar badge), or every row redraws on any `git status`. Hand rows plain values (`RepoRowOptions`; `ProcessRow`/`FavoriteRow` get `isFavorite`/`isBusy` and keep `PortModel` unobserved) and keep the store unobserved. The same goes for shared singletons: rows don't observe `ExpandedRepo`/`ExpandedServer` (each row observes its own `row(_:)` object, and the list uses `onReceive`), `ModifierKeys` (only the small view that shows ⌥, like `CommitLabel` and `StopButton`) or `BackgroundClaude` (the list hands each row its sessions). Observing them made a click on one row, a modifier key or a scan go over the whole list (60–225 ms). Don't publish state that changes on every timer tick unless the view shows it (`PortModel.isScanning`). Charts get one accessibility element (`.accessibilityElement(children: .ignore)` with a label and value): with an element per mark, SwiftUI rebuilt them all on every new sample. Measure with a run loop observer logging passes over a frame, and `xctrace record --template "Time Profiler" --attach Bridge`; `sample` alone doesn't show which pass the time was in.

## Conventions

- Doc comments explain *why* (often a macOS quirk or workaround) in plain prose; keep that style when touching such code.
- Commit messages: short imperative English summary line (e.g. "Track ⌥ key state with a monitor so the commit button updates").
